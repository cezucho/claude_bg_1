# ADR-0005: Hex Coordinate System and Pattern Representation

## Status

Accepted (2026-08-14) · **Amended 2026-08-17 — tier-4 pattern orientation**

## Summary

Every spatial rule in the game resolves through the hex model, and the ladder's
targeting-rigidity tiers require patterns that are rotatable at tier 3 and fixed in
absolute board orientation at tier 4. This ADR adopts **axial coordinates with a
flat-top layout**, patterns stored as offset lists, and rotation as a pure function.

## Context

### Problem Statement

`initiative-ladder.md` Core Rule 5 makes targeting rigidity the mechanism that stops
play collapsing toward low initiative: tier 1–2 abilities target freely, tier 3 uses a
**rotatable** pattern, and tier 4 uses a **fixed** pattern in absolute board
orientation that cannot be rotated. Tier 4's power budget is justified precisely by how
often it is *not* legal.

That makes pattern representation a gameplay-critical decision rather than a utility
choice. It also makes `applicability(i)` — F4's assumption that tier-4 patterns are
legal in roughly 30% of board states — a measurable property of this representation.

### Current State

No code. The prototype used axial coordinates with the standard distance metric, and
that choice survived contact with the design. It also produced a cautionary bug: move
targets were generated by iterating a fixed direction list and truncating, which biased
one team's movement so severely it looked like a first-mover advantage
(`prototypes/initiative-ladder/REPORT.md`, Round 3).

### Constraints

- Integers only (ADR-0002). Cube and axial coordinates are integral; offset
  coordinates make neighbour arithmetic conditional on parity and are error-prone.
- `HexCoord` is embedded in `Champion` inside a blittable struct (ADR-0003), so it must
  be a small value type with no reference members.
- Board radius is small (single digits); no spatial index is warranted.

### Requirements

- Distance, neighbours, line, and range queries (TR-CONCEPT-004).
- Rotatable patterns at tier 3, fixed absolute patterns at tier 4 (TR-LADDER-009).
- Patterns affect allies and enemies identically by default (TR-LADDER-010).
- Off-board pattern hexes are ignored; the ability stays legal if any legal target
  remains (ladder GDD, Edge Cases).

## Decision

**Axial coordinates `(q, r)`, flat-top hex layout, with the implicit cube coordinate
`s = −q − r`.**

```csharp
public readonly record struct HexCoord(int Q, int R)
{
    public int S => -Q - R;

    public static int Distance(HexCoord a, HexCoord b)
        => (Math.Abs(a.Q - b.Q) + Math.Abs(a.S - b.S) + Math.Abs(a.R - b.R)) / 2;
}
```

**Patterns are stored as an ordered list of offsets** relative to the acting champion,
in a canonical orientation **whose forward direction is +R**. Tier 3 rotates the offset
list through any of six facings; tier 4 does not rotate, but **is reoriented to the acting
team's forward direction** — identity for the team advancing toward +R, a half-turn for
the team advancing toward −R.

```csharp
public static HexCoord RotateClockwise(HexCoord offset)   // 60°, exact, integer
    => new(-offset.R, -offset.S);
```

Six applications return to the identity, which is a cheap invariant to test.

### Architecture

```
   Ability definition (content, immutable)
   ┌──────────────────────────────────────┐
   │ RigidityTier : 1 | 2 | 3 | 4         │
   │ Offsets      : HexCoord[]  (canonical orientation)
   └───────────────┬──────────────────────┘
                   │
        ┌──────────┴──────────┐
        │ tier 1-2            │ tier 3                    │ tier 4
        │ free target in range│ rotate offsets × 6 facings│ apply offsets verbatim
        └──────────┬──────────┴───────────┬───────────────┴────────┐
                   ▼                      ▼                        ▼
              candidate target hexes ──► filter: on-board ──► filter: occupied
                                                          ──► TARGET SET
                            (empty target set ⇒ ability is not legal — F1)
```

### Key Interfaces

```csharp
public static class Hex
{
    /// Canonical neighbour directions. Order is fixed for determinism, and
    /// callers MUST consume all six — see Implementation Guidelines.
    public static ReadOnlySpan<HexCoord> Directions => new HexCoord[]
    {
        new( 1, 0), new( 1,-1), new( 0,-1),
        new(-1, 0), new(-1, 1), new( 0, 1)
    };

    public static int Distance(HexCoord a, HexCoord b);
    public static bool InBoard(HexCoord h, int radius);
    public static HexCoord Rotate(HexCoord offset, int steps);   // steps mod 6

    /// Half-turn about the origin, (q,r) → (−q,−r). The board's symmetry map, and
    /// exactly Rotate(offset, 3). See the amendment below.
    public static HexCoord HalfTurn(HexCoord h);

    /// Reorients a canonical-frame pattern offset for the acting team. Tier 4 only.
    public static HexCoord ForForward(HexCoord offset, bool forwardIsPositiveR);
}

public static class Targeting
{
    /// Resolves a pattern into concrete board hexes. Off-board hexes are dropped.
    /// Returns empty when the pattern does not line up — the common, intended
    /// case for tier 4.
    public static void ResolvePattern(
        in MatchState state, HexCoord origin, ReadOnlySpan<HexCoord> offsets,
        RigidityTier tier, int facing, Span<HexCoord> results, out int count);
}
```

### Amendment: team-relative tier-4 patterns

**The problem.** Map & Terrain places the two teams across opposite *edges* and fixes the
board's symmetry as a 180-degree rotation, `(q,r) → (−q,−r)`. Team A advances toward `+R`;
team B advances toward `−R`. Under the original rule a tier-4 pattern resolved to the same
world-space shape for both, so a wedge that opened toward the enemy for team A opened
toward its own nexus for team B. The ability would not be the same ability.

**The fix.** Tier-4 offsets are authored in a canonical frame with forward `= +R`, and
`ForForward` applies a half-turn for the team facing the other way.

**Why this works, and why it barely required anything.** The half-turn is *exactly*
`Rotate(offset, 3)` — it is a rotation, already expressible by the six-facing machinery
tier 3 uses, integer-exact, and shape-preserving. It is also the same map that defines the
board's symmetry, so a pattern played by the far team at the antipodal origin covers
exactly the antipodal hexes. No new geometry was needed; the amendment is a frame change,
not a mechanism.

**Why a mirrored board would have made this impossible.** A reflection is not a rotation.
A chiral pattern's mirror image is reachable by *none* of the six facings, so on a
mirror-symmetric board the two teams would hold genuinely different-shaped versions of the
same ability, and no orientation rule could fix it — the content itself would have to be
authored twice. **Rotational symmetry is therefore not an aesthetic choice about the map;
it is what makes a shared ability library possible at all.** This is asserted directly in
`PatternOrientationTests.MirroredPattern_IsReachableByNoRotation`.

**Scope.** Tier 4 only. Tiers 1–2 target freely and tier 3 chooses among all six facings,
so both teams already reach the same set; neither is affected.

### Implementation Guidelines

- **Never truncate a generated action or target set along an ordered axis.** This is
  not a style note. `prototypes/initiative-ladder/REPORT.md` records that capping move
  targets to the first six of a direction-ordered list made one team unable to move
  toward the map's objectives, producing what looked for three rounds like a 70%
  first-mover advantage. If a set must be capped, cap it by a symmetric criterion or
  randomly — never by generation order.
- Patterns are content, not code (ADR-0007). Adding a champion never means editing
  targeting logic.
- Rotation is integer-exact; there is no trigonometry anywhere in the simulation.
- Board bounds are a radius test against the origin, not a rectangle.
- Presentation converts axial to world space on its own side. The simulation has no
  concept of world position.

## Alternatives Considered

### Alternative 1: Offset (row/column) coordinates

- **Description**: Store hexes as row and column with odd/even row offsetting.
- **Pros**: Maps directly to a 2D array; intuitive for level authoring.
- **Cons**: Neighbour and distance calculations become parity-dependent, which is a
  classic and persistent source of bugs. Rotation is not expressible as simple
  arithmetic — fatal for tier-3 patterns.
- **Estimated Effort**: Comparable to write, considerably higher to debug.
- **Rejection Reason**: Rotation is a gameplay requirement, and offset coordinates
  make it awkward exactly where it needs to be reliable.

### Alternative 2: Full cube coordinates `(x, y, z)` stored explicitly

- **Description**: Store all three cube components.
- **Pros**: Rotation and reflection are trivially symmetric; distance is clean.
- **Cons**: 50% larger per coordinate for a value derivable in one subtraction. With
  `HexCoord` embedded ten times inside a struct cloned ~19,000 times per round, size is
  not free.
- **Estimated Effort**: Identical.
- **Rejection Reason**: Axial gives the same maths at two-thirds the size; `S` is a
  computed property.

### Alternative 3: Godot's `TileMapLayer` and navigation services

- **Description**: Model the board with engine tilemap and navigation nodes.
- **Pros**: Editor tooling; built-in pathfinding.
- **Cons**: Violates ADR-0001 outright — the board would live in the engine and become
  unavailable to headless tests and the AI.
- **Estimated Effort**: Lower for authoring, impossible for the architecture.
- **Rejection Reason**: Breaks the simulation boundary. Presentation may use a
  `TileMapLayer` for *rendering* the board it is told about.

## Consequences

### Positive

- Distance, neighbours and rotation are a handful of integer operations, exact and
  deterministic.
- Tier-3 rotation is one pure function applied up to six times — trivially testable,
  with a clean identity invariant.
- Patterns being data means the Ability Schema GDD can define geometry without touching
  code, and the Balance Harness can measure real `applicability` values against F4's
  30% assumption.
- No engine dependency, so the board is fully available to headless tests.

### Negative

- Axial coordinates are less immediately readable than row/column for anyone authoring
  a map by hand. The content pipeline should offer a friendlier view.
- Board bounds as a radius means non-hexagonal map shapes need an explicit hex set
  rather than a bound — acceptable, and deferred to the Map & Terrain GDD.

### Neutral

- Flat-top versus pointy-top is a presentation choice with no rules consequence; it is
  fixed here only so that content authors and artists share one convention.

## Migration Plan

Greenfield. The prototype already used this coordinate system, so its findings carry
over directly — including its bug, which is why the prohibition above exists.

**Rollback plan**: Coordinate systems are convertible by pure function, so a change
would be mechanical but would touch every spatial call site. Not expected.

## Validation Criteria

- [ ] `Distance(a, b) == Distance(b, a)` for all board pairs.
- [ ] `Rotate(offset, 6) == offset` for all offsets.
- [x] A tier-4 pattern produces identical absolute hexes regardless of champion *facing*
      — but **not** regardless of team; see the next three.
- [x] `HalfTurn(h) == Rotate(h, 3)` for every offset, and `HalfTurn` is an involution that
      preserves distance. *(`PatternOrientationTests`)*
- [x] A tier-4 pattern played by the far team at the antipodal origin covers exactly the
      antipodal hex set. *(`TeamRelativePattern_CoversAntipodalHexes`)*
- [x] A chiral pattern's **half-turn** is reachable by one of the six facings; its
      **mirror** is reachable by none. *(`HalfTurnedPattern_IsReachableByRotation`,
      `MirroredPattern_IsReachableByNoRotation`)*
- [ ] A tier-3 pattern produces exactly six distinct target sets across facings, unless
      the pattern is rotationally symmetric.
- [ ] **Mirror-match test**: two teams with identical drafts on a mirrored board win
      within 50% ± 5% over 200 matches. Any larger deviation is a harness or
      symmetry bug until proven otherwise.
